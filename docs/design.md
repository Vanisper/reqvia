# 项目设计

Reqvia 是可扩展的 HTTP 客户端库，以稳定的执行契约连接业务接口与传输实现。项目围绕业务接口组织、请求执行与能力组合展开：调用方用普通函数或 Service 表达业务，执行核心统一处理调用生命周期，扩展模块接入所需的传输与策略。

## 使用者与价值

业务开发者需要清晰地组织接口输入输出，在多个调用中复用协议与配置，并一致地处理失败和取消。扩展开发者需要稳定的执行与传输接口，将认证、重试、测试替身或新的请求器接入调用链。这些使用方式共用同一套契约，不要求调用方了解底层任务对象和回调结构。

Reqvia 集中处理调用方会反复遇到的执行问题：配置如何合并，输入何时固定，状态失败如何传播，超时如何覆盖解码，以及取消后如何处理迟到结果。统一这些规则后，业务代码可以专注于接口路径、领域模型和业务成功条件，扩展模块可以围绕确定的行为组合能力。

业务接口跨运行环境复用、在不同请求器之间切换，以及使用内存替身测试，都来自这种职责划分。运行环境通过适配器接入，具体环境的支持范围由适配器能力与验证记录描述。

## 职责划分

| 模块         | 负责的内容                                       | 对外接口                                                              |
| ------------ | ------------------------------------------------ | --------------------------------------------------------------------- |
| 客户端核心   | 配置快照、请求规范化、状态判断、取消、超时与终态 | `createHttpClient`、`HttpExecutor`、`Transport`                       |
| 编解码       | 请求正文编码、响应解析与业务校验组合             | `jsonBody`、`textBody`、`bytesBody`、`json`、`text`、`bytes`、`empty` |
| 传输适配器   | 平台调用、响应映射、物理取消与能力检查           | 实现 `Transport` 的工厂                                               |
| 执行组合     | 认证上下文、重试预算与并发协调                   | 围绕 `HttpExecutor` 组织的应用或扩展模块                              |
| 取消桥接     | 自有取消契约与平台信号的转换、监听清理           | 独立兼容包                                                            |
| 测试工具     | 可控响应、失败、延迟与取消观察                   | 内存 `Transport`                                                      |
| 应用 Service | 接口路径、领域方法、业务信封与模型转换           | 普通类或函数                                                          |

客户端核心和编解码同属 `reqvia` 主包。核心定义公共契约，编解码依赖这些契约；适配器、兼容包与测试工具依赖主包。主包不反向导入这些扩展，应用初始化代码负责选择和组装它们。

## 执行接口

客户端以 `request(spec, decoder, options)` 执行一次请求。

- `spec` 描述 HTTP 意图：地址、方法、查询参数、头字段与已编码正文
- `decoder` 声明响应表示，并将响应内容解释为调用方需要的数据
- `options` 控制本次调用的取消、超时与状态接受规则

这三个部分分别表达“发送什么”“如何理解响应”和“如何控制调用”。拆分后，同一解码器可以被多个业务接口复用，调用控制可以沿 Service 传递，传输适配器可以专注于报文转换。

请求描述使用普通数据与字节数组。客户端在调用时复制可变容器与字节正文，使调用后的输入修改不影响已开始的请求。取消对象继续传递控制状态；解码器的表示与函数引用在调用时固定，闭包内部状态由调用方管理。数据结构可被复制不代表请求天然适合共享或重试；这些行为还取决于身份、HTTP 语义和业务副作用。

`HttpExecutor` 只提供请求执行接口，便于 Service 注入、应用包装与测试替换。客户端另提供 `derive` 创建配置快照。接口复用通过普通函数和 Service 完成，核心保持一条执行入口。

## 响应与业务协议

响应表示只有文本和字节两种。传输适配器交付声明的表示，解码器据此接收确定的输入类型。

`json()` 解析文本，未提供校验函数时返回 `unknown`；业务校验与转换函数决定最终结果类型。`text()` 返回文本，`bytes()` 返回字节。`empty()` 使用文本表示，确认正文为空字符串后返回 `null`；空正文与合法 JSON 是不同的响应契约。

HTTP 状态判断先于成功解码。适配器收到可交付的 HTTP 响应时，包括 4xx 与 5xx，都返回中立报文；客户端依据状态接受规则决定是否继续解码。状态不被接受时保留响应信息，供应用按自己的错误协议读取。

业务成功码、响应信封与领域模型由业务解码器解释。例如某个后端将结果放在 `result` 中，相关 Service 可以使用专门的解码器完成校验与提取。主包不读取固定的业务字段，也不要求实体继承或特定校验库。

## 调用生命周期

一次客户端调用至多执行一次 `Transport.send`，随后进行状态判断与解码，最终只提交一次成功或失败。输入不合法、提前取消或预算已耗尽时，可以在传输前结束。

取消控制独立于 Promise。调用方持有 `CancellationSource`，向下游传递其 `cancellation`；客户端主动订阅取消，并通知适配器停止底层任务。即使底层任务未能立即停止，调用方也能按取消契约结束等待，迟到结果不能改变已提交的终态。

超时覆盖本次调用的规范化、传输和异步解码。客户端同时使用计时通知与阶段检查：计时通知让悬挂的异步工作能够结束等待，阶段检查阻止超时后的结果提交。同步执行的代码无法被定时器强制中断，因此解码器应专注于转换数据，将页面和会话副作用留给上层。

Reqvia 自身产生的失败使用可分类的 `HttpError`。用户提供的状态判断、解码和校验函数抛出的错误原样传播，使应用可以保留领域错误的类型与信息。库不会因为展示提示或记录日志而吞掉失败。精确的错误分类与竞态顺序见[公共契约](contracts.md)。

## 传输扩展

核心理解 HTTP 的方法、URL、头字段、状态与正文，使用自有的请求、响应和取消契约。平台类型、原生任务与专用配置留在对应适配器的构造接口中。

应用显式注入运行能力，例如为 Fetch 适配器提供 `fetch` 与创建 `AbortController` 的函数。适配器将取消连接到平台任务，将原生结果映射成中立报文。核心无需探测 `window`、`uni` 或全局请求器，也不通过未知参数袋传递平台配置。

相同请求在不同适配器中遵循相同的执行契约；目标端无法满足请求方法或正文表示时，以 `UNSUPPORTED` 明确拒绝。文本是平台交付的解码结果，字节必须来自平台的二进制响应，不能通过重新编码文本冒充。各端实际可用的能力由验证记录确定。

初期传输实现包括 Fetch、UniApp 与内存适配器。Fetch 与 UniApp 用于验证真实请求，内存适配器用于控制响应、失败与时序；三者共同检验 `Transport` 能否承载不同实现。其他请求器和运行环境可以实现同一接口，并按自身能力接受契约验证。

浏览器、Node 和选定的 UniApp 目标端是首批验证环境。模拟传输、真实网络和具体目标端分别记录证据，使调用方能够据此判断某个适配器的可用范围。

## Service 与上层协调

Service 可以是普通类，也可以是函数集合。它注入 `HttpExecutor`，为每个领域方法构造请求、选择解码器并透传调用控制；生命周期状态保留在每次调用中，使同一实例能够安全地承接并发调用。

认证上下文由应用捕获并注入。需要检查会话有效性时，应用围绕执行器统一处理成功与失败路径，确认结果仍属于原来的身份后再产生业务副作用。账号、租户和凭证结构属于应用协议，核心不增加通用作用域字段。

重试、认证恢复和共享请求需要独立的协调语义。负责这些行为的上层模块应统一管理总时间、尝试次数、输入快照与取消归属。共享身份必须包含所有影响结果的因素；方法和 URL 相同不足以证明请求可以共享。页面是否接收旧结果、写入后哪些读取失效，则由拥有状态的模块决定。

可复用的协调能力可以形成独立扩展模块，业务特有的凭证获取、身份判断和失效关系通过明确的接口传入。扩展模块与应用包装器遵循相同的执行契约，核心保持单次调用的职责。

接入查询状态库时，Service 返回普通 Promise，通过取消桥接接收上层信号。缓存、订阅、重试和失效分别由明确的一层管理，避免相互独立的重试或缓存叠加。会话切换、共享消费者退出和写后旧读取用于验证相应扩展的组合行为，相关结果提交规则由管理状态的模块明确约定。

## 文件能力

缓冲在内存中的二进制请求与响应使用字节表示。原生文件上传、下载落盘、进度和流式处理由独立平台扩展承接，它们需要各自的资源关闭、容量与取消契约。

业务 Service 可以注入 `AvatarUploader`、`ReportDownloader` 等领域文件能力。浏览器文件对象、Node 文件路径与 UniApp 临时路径保留在对应实现中，普通 HTTP 执行接口只处理报文。文件扩展可以复用取消与错误基础能力，但不进入首版执行核心。

## 工程组织与验证

项目采用 monorepo，使用 Vite Plus 统一组织开发、检查、测试与构建。当前工程骨架包含 `apps/website` 与 `packages/utils`，工作空间同时保留 `tools/*`。HTTP 产品包规划为 `reqvia` 主包、Fetch 适配器、UniApp 适配器、取消桥接与测试工具；应用和示例作为不发布的 workspace 包消费公共入口。

包的划分对应运行依赖与使用场景。业务可以只安装所需的传输实现，主包保持平台无关；同一仓库中的契约测试与集成示例检查跨包组合，避免适配器与主包各自满足局部测试却无法协同工作。目录与依赖规则见[项目结构](structure.md)。

初期实现以完整的单次执行链、业务使用方式与传输扩展验证为完成条件。测试通过公共接口检查行为，包括配置快照、状态失败、解码失败、主动取消、超时和迟到结果；集成示例验证 Service 与执行器组合，适配器能力按具体环境记录。实施阶段与验收条件见[实施与验收](implementation.md)，环境证据见[平台兼容性](compatibility.md)。
