# 实施与验收

Reqvia 的开发以可运行的业务调用闭环为单位推进。工程初始化验证工具链，产品验收验证请求行为，两者分别记录。产品设计见[项目设计](design.md)，精确语义见[公共契约](contracts.md)。

当前已完成请求核心、Fetch 与 UniApp 两种传输，以及原生取消信号双向桥接。Web、UniApp 与 Node 三个消费端共享一份领域 Service，分别验证页面、页面生命周期和进程退出中的请求控制；四个产品包均从独立安装的 tarball 检查类型和运行入口。平台证据见[兼容性记录](compatibility.md)。后续根据实际业务中重复出现的协调需求确定扩展边界。

## 工程基线

工作区通过 `vp create vite:monorepo` 建立，保留 CLI 的目录、配置和示例。初始化交付包含本地 Git 仓库、依赖锁文件、检查与构建命令。

完成条件：

- `vp install --frozen-lockfile` 可以复现依赖
- `vp run ready` 完成构建、检查、测试和独立打包产物消费
- 库声明和应用产物生成在各自的 `dist/`

这一步通过后，工具链可以承载产品开发。模板函数的测试通过不代表任何 HTTP 行为已经实现。

## 建立首个请求闭环

通过 CLI 添加 `packages/reqvia`，先实现一个普通 Service 可以调用的完整路径：客户端配置、请求快照、URL 与头字段规范化、`Transport`、状态判断、解码和统一响应。首个内存实现与首个真实传输一起检验接口，避免只为测试替身设计契约。

完成条件：

- 一个 Service 通过 `HttpExecutor` 调用接口，并返回经过校验的领域对象
- 同一 Service 可替换内存传输和真实传输，业务代码不变
- 文本、字节、JSON、空响应各有明确的成功与失败行为
- 状态失败保留中立响应；用户解码器抛出的领域错误保持原值
- 发布入口可以生成声明，并被独立消费工程解析

接口中没有实际使用收益的抽象不进入公开导出。优先让一条调用路径成立，再扩大接口数量。

## 完整实现调用生命周期

在已有闭环上补齐输入快照、取消、总预算、资源释放与迟到结果处理。它们是每次请求都适用的基础行为，在增加重试与共享之前完成。

| 场景                                | 必须观察到的结果                   |
| ----------------------------------- | ---------------------------------- |
| 发送前取消                          | Promise 拒绝，`send` 未被调用      |
| 传输永不结束                        | 取消或超时仍能结束外层等待         |
| 异步解码永不结束                    | 取消或超时仍然有效                 |
| 同步解码跨过 deadline               | 恢复执行后拒绝超时，不提交成功     |
| 取消与 deadline 同时可见            | 按公共契约的统一优先级判定         |
| 终态后收到成功或失败                | 结果不改变，也不产生未处理的拒绝   |
| 调用后修改 query、headers、字节正文 | 已开始的请求不受影响               |
| 调用结束且从未取消                  | 计时器、取消监听和桥接监听得到释放 |

用可控时钟验证时间边界，避免依赖真实毫秒延迟的偶然结果。时钟与调度是内部测试替换点，不为测试方便扩大业务接口。

## 验证传输扩展

将第二种传输接入同一套契约测试，检验平台特有对象是否仍留在适配器中。初期选择 Fetch 与 UniApp 作为不同机制的适配对象；后续目标按实际使用需要加入。

每个适配器需要完成：

- 输入映射、响应表示与错误归一化的模拟测试
- HTTP 状态失败与网络失败的区分
- 完整读取正文期间的取消与超时验证
- 真实目标中的文本、二进制与空响应验证
- 明确目标、版本、能力限制与验证证据的记录

跨环境验证使用[平台兼容性](compatibility.md)中的矩阵。未运行的目标保持“未验证”；其他环境的通过结果不替代该目标的证据。

## 验证业务组合

在 `examples/` 中维护消费公共入口的应用，`apps/transport-check` 保留传输能力验收。页面、Service 和状态拥有者各自履行契约，检验核心接口是否足以接入实际业务。

| 场景              | 责任与验收                                                   |
| ----------------- | ------------------------------------------------------------ |
| 函数与 Service 类 | 同一领域方法可注入执行器，取消参数贯穿调用链                 |
| 会话切换          | 应用保存会话代次；旧请求的成功与失败均不能修改新会话         |
| 页面延迟写入      | 状态拥有者在写入处确认代次，不能只依赖 HTTP 完成检查         |
| 查询库接入        | 信号能够桥接并释放监听；错误保持拒绝；缓存和重试由约定层管理 |
| 共享读取          | 共享层分别处理消费者结束与底层任务取消                       |
| 写后旧读取        | 状态层按资源关系失效，在结果提交处拒绝过期代次               |

已有示例完成函数、Service、领域校验、查询代次和生命周期取消的组合验证。Web 的状态测试包含不响应取消的替身，让迟到成功和失败仍到达状态层，从而验证提交处的代次保护。Node 使用真实子进程验证 SIGINT、SIGTERM、超时与自然退出。浏览器验收同时观察页面状态和服务端连接结束。

后续按以下场景扩展业务验证：

- 会话切换后，旧请求的成功和失败不能修改新会话
- 多个消费者共享一次读取，单个消费者退出时不影响其他消费者
- 写入成功后，先发出的旧读取不能覆盖新状态

这些场景先在消费示例中建立可运行验收，重复的协调逻辑再抽取为有独立契约的扩展包。查询库集成和 `@reqvia/testing` 随实际需求接入，不预先扩大核心接口。

## 首版交付条件

首版交付的是经过验证的请求客户端与选定适配器。文件传输、流、自动刷新、通用重试和共享框架各有额外语义，按独立能力交付。

- 公共类型、示例与实现一致，Service 示例可以编译并运行
- 核心契约、生命周期、适配器映射与真实传输验证分别通过
- 主包不暴露平台类型；跨包只通过公开入口访问
- 干净环境可通过 Vite Plus 命令完成安装、检查、测试和构建
- 打包产物可独立安装，运行入口与类型声明都能解析
- 平台兼容记录列明实际目标与限制，不扩大验证结论

设计和实现冲突时，定位差异的原因，明确修正契约或实现，并让对应测试表达同一行为。测试用于验证产品契约，不自动拥有修改产品语义的决定权。
